# 자체 피드백 기록

시작: 2026-08-27

## 라운드 0 · 착수 전 상태 점검

코드 감사 결과 확인된 공백:
- 기록 저장 없음 (localStorage/indexedDB 미사용) → 앱 종료 시 전량 소실
- 서비스워커 없음 → 오프라인 실행 불가
- Wake Lock 없음 → 측정 중 화면 꺼짐
- 이상 채널 감지 없음 → 끊김/포화 채널을 사용자가 알 수 없음
- 원시값 실시간 조회 화면 없음 → 하드웨어 브링업 시 진단 불가
- 내보내기 없음 → 실측 데이터 전달 수단 없음

착수 순서: 진단 화면 → 채널 상태 → 저장 → 내보내기 → Wake Lock → 오프라인

## 라운드 1 · 구현 후 첫 기능 검증

정상 동작 확인: 모듈 3개 로드, 진단 표 16행, 저장 1건, 기록바 표시,
경고줄 조건부 숨김, Wake Lock 지원 감지, localStorage 가용.

### 발견 1 — 실제 주기(Hz) 를 잘못된 지점에서 재고 있음  [수정함]
`markFrame()` 을 화면 갱신 루프에서 호출하고 있었다. 이러면 **데이터 수신
주기가 아니라 화면 그리는 주기**를 재게 된다. 시뮬레이터에서는 두 값이
같지만, 실제 BLE 를 붙이면 완전히 달라진다. 패킷이 안 와도 화면은 계속
그려지므로 "30Hz 수신 중"이라고 거짓 표시된다.

진단 화면의 존재 이유가 "데이터가 오고 있는가"를 보는 것인데, 그 값이
거짓이면 화면 자체가 무의미하다.

→ 데이터가 들어오는 지점(sensor)으로 옮김.

### 발견 2 — 테스트 환경에서 Hz 가 125 로 측정됨  [아티팩트, 조치 불필요]
헤드리스에서 rAF 를 setTimeout 으로 대체했기 때문. 실제 브라우저에서는
정상. 다만 발견 1 때문에 어차피 측정 지점을 옮김.

## 라운드 2 · 실패 경로 검증 (고장 주입)

ch3 을 강제로 0, ch7 을 강제로 1023 으로 만들어 검증.

정상 동작: dead=1 / sat=1 / ok=14 로 정확히 판정. 경고줄 자동 표시.
CSV 25열(메타 9 + 채널 16) 정상.

### 발견 3 — 영점 보정 직후 값이 0 으로 떨어지지 않음  [수정함]
영점을 잡은 직후 raw 443 → 보정 298. 0 에 가까워야 정상이다.

원인 두 가지:
1. 떨림 완화(이동평균) 버퍼에 **영점 잡기 이전의 큰 값들이 남아 있어서**
   평균이 0 으로 내려오지 않는다.
2. 영점을 **단 한 프레임**의 값으로 잡고 있다. FSR 은 값이 계속 떨리므로
   하필 튄 순간에 잡으면 기준선 자체가 틀어진다.

실물에서는 이게 좌우 비교를 통째로 망가뜨린다. 기준선이 센서마다
제각각 잘못 잡히기 때문이다.

→ 최근 창의 평균으로 영점을 잡고, 잡는 즉시 완화 버퍼를 비우도록 수정.

## 라운드 3 · 적대적 검토 — 실물에서 무엇이 깨지나

저장 왕복·필드 보존·50건 상한·삭제 모두 정상. 진단 화면 판정 정확
(ch3 끊김, ch15 포화 자동 표시).

### 발견 4 — 데이터가 끊겨도 "수신 중 30Hz" 로 계속 표시됨  [수정함]  ★심각
`actualHz()` 가 마지막 수신 시각을 보지 않고 과거 타임스탬프 평균만
돌려준다. BLE 가 끊겨서 패킷이 안 와도 **화면에는 정상 주기가 그대로
표시된다.**

진단 화면의 존재 이유가 "데이터가 오고 있는가"를 보는 것인데, 정작
끊김을 못 잡아낸다. 하드웨어 브링업에서 가장 자주 겪을 상황이 바로
이것이라 치명적이다.

→ 마지막 수신이 1초 이상 지나면 0Hz 로 보고하고, 상태를 '끊김'으로
   표시하도록 수정.

### 발견 5 — 채널 오류값(0xFFFF) 미처리  [수정함]
DATA_CONTRACT 에 0xFFFF 는 채널 미연결/오류로 정의해 두었는데
앱이 이를 모른다. 65535 가 들어오면 히트맵 색 계산과 합계가 전부
망가진다. 규격은 정의했으면서 구현을 안 한 셈.

→ 수신 단계에서 오류값을 걸러 '끊김' 으로 처리.
