# 2단계 · 블루투스 모듈 테스트

센서 → 아두이노 → 블루투스 → 휴대폰 경로가 끝까지 이어지는지 확인한다.
**1단계(센서 포화 테스트)가 끝난 뒤에 한다.** 센서값이 USB 로 안 나오는데
무선부터 붙이면 어디가 문제인지 알 수 없다.

---

## 0. 먼저 — 어떤 모듈인지부터 확인한다

**이 확인을 건너뛰면 며칠을 날릴 수 있다.** 블루투스 모듈은 겉모습이
비슷해도 속이 두 종류이고, **한 종류는 이 프로젝트의 앱과 연결이 안 된다.**

| 구분 | 흔한 이름 | 웹 앱 연결 | 비고 |
|---|---|---|---|
| **BLE** (저전력) | HM-10, AT-09, BT05, JDY-08 | **가능** | 칩이 CC2541 / CC2540 |
| **클래식 SPP** | HC-05, HC-06 | **불가능** | 브라우저가 SPP 를 지원하지 않음 |

판별 방법 (쉬운 순서대로)

1. **모듈에 적힌 글자를 본다.** `HC-05`·`HC-06` 이면 클래식이다
2. **휴대폰 블루투스 설정에서 검색해 본다.**
   - 설정의 일반 기기 목록에 뜨고 "페어링" 을 요구하면 → 클래식
   - 설정에는 안 뜨는데 `nRF Connect` 같은 BLE 앱에서만 보이면 → BLE
3. **AT 명령으로 묻는다.** 아래 `at_check` 로 `AT+VERSION` 또는 `AT+VERR?`

**클래식(HC-05/06)이었다면** — 그 모듈로는 이 앱에 연결할 수 없다.
BLE 모듈(AT-09 / HM-10)을 따로 사야 한다. 몇 천 원이고 배선은 동일하다.
다만 아래 A·B 테스트는 클래식으로도 그대로 되므로, 모듈이 살아 있는지와
센서값이 무선으로 나가는지는 지금 확인해 둘 수 있다.

---

## 1. 배선

```
모듈 VCC → 아두이노 5V      (모듈에 3.3V 전용이라 적혀 있으면 3.3V)
모듈 GND → 아두이노 GND
모듈 TXD → 아두이노 2번 핀
모듈 RXD → 아두이노 3번 핀    ※ 아래 분압
```

### 지켜야 할 것 두 가지

**① 0·1번 핀에 꽂지 않는다.**
0·1번은 USB 업로드가 쓰는 선이다. 거기 모듈을 꽂으면 업로드가 실패하거나
값이 섞인다. 2·3번으로 빼고 소프트웨어 시리얼을 쓴다.

**② 모듈의 RXD 는 분압해서 넣는다.**
아두이노가 내보내는 신호는 5V 인데 모듈 입력은 3.3V 기준이다.

```
3번 핀 ──── 1kΩ ────┬──── 모듈 RXD
                     │
                    2kΩ
                     │
                    GND
```

브레이크아웃 보드 대부분은 5V 를 견디지만, 저항 두 개로 확실히 해 두는 편이
모듈을 태우는 것보다 싸다. **TXD 쪽은 분압하지 않는다** — 모듈이 내보내는
3.3V 를 아두이노가 그대로 읽는다.

## 2. 테스트 A — 모듈이 살아 있는가 (`at_check`)

1. `at_check` 폴더를 폴더째로 열어 업로드
2. 시리얼 모니터 열기, 속도 **9600**
3. 입력칸 옆 줄 끝 설정을 **"Both NL & CR"** 로 바꾼다 ← 안 하면 응답이 없다
4. `AT` 입력

| 결과 | 뜻 | 다음 |
|---|---|---|
| `OK` | 모듈 정상 | 3번으로 |
| 아무 반응 없음 | 속도 불일치 또는 배선 | 아래 참조 |
| 글자가 깨짐 | 속도 불일치 | 38400 · 115200 로 바꿔 시도 |

**아무 반응이 없을 때 확인 순서**

1. 줄 끝 설정이 "Both NL & CR" 인가
2. `bt.begin(9600)` 의 숫자를 38400, 115200 으로 바꿔 재업로드
3. **TXD 와 RXD 를 서로 바꿔 꽂아 본다** — 가장 흔한 실수다
4. 모듈의 LED 가 깜빡이는가 (안 깜빡이면 전원 문제)
5. HC-05 는 보통 **버튼을 누른 채 전원을 넣어야** AT 모드로 들어간다

알아 둘 만한 명령

```
AT            → OK
AT+VERSION    → 펌웨어 버전 (모델 확인)
AT+NAME       → 기기 이름 조회
AT+NAMEinsole → 이름 변경 (휴대폰에서 찾기 쉬워진다)
```

## 3. 테스트 B — 센서값이 무선으로 나가는가 (`bt_sensor_stream`)

1. 1단계 센서 회로를 그대로 둔 채 `bt_sensor_stream` 업로드
2. 휴대폰에 시리얼 터미널 앱 설치
   - BLE 모듈 → **nRF Connect** 또는 **Serial Bluetooth Terminal**
   - 클래식 모듈 → **Serial Bluetooth Terminal** (안드로이드만)
3. 모듈에 연결 (클래식은 페어링 번호 `1234` 또는 `0000`)
4. 숫자가 흐르기 시작하면 성공

| 봐야 할 것 | 정상 |
|---|---|
| 숫자가 1초에 10번쯤 흐른다 | ✓ |
| 센서를 누르면 숫자가 따라 올라간다 | ✓ |
| USB 시리얼 모니터의 값과 같다 | ✓ |

**세 번째가 핵심이다.** USB 값과 무선 값이 같으면 경로 전체가 정상이다.
다르면 무선 구간 문제, 둘 다 이상하면 센서 쪽 문제다.

## 4. 여기까지 되면

센서·아두이노·블루투스·휴대폰이 전부 확인된 것이다. 남은 것은

1. **8채널로 늘리기** — 우노는 아날로그 핀이 A0~A5 여섯 개뿐이다.
   나노(A0~A7) 또는 멀티플렉서(CD74HC4067)가 필요하다
2. **규격 패킷으로 바꾸기** — `hardware/step3_packet_stream` 에 준비되어 있다
3. **앱에 연결** — 안드로이드 크롬에서
   https://heonchris.github.io/claude-test-project/ 접속 → [인솔 연결]

`step3_packet_stream` 을 올리면 앱 히트맵의 **왼발 엄지 한 곳**이
센서를 따라 움직인다. 그 한 점이 보이면 경로 전체가 증명된 것이다.

> 과거에 있던 두 가지 문제는 이미 고쳐져 있다.
> **① UUID** — 앱이 FFF0 만 찾아서 시중 모듈(FFE0)을 못 찾던 문제.
> **② 20바이트 분할** — 34바이트가 쪼개져 전부 버려지던 문제.
> 둘 다 `js/11-ble.js` 에서 처리한다. 자세한 내용은 `DATA_CONTRACT.md` 2절.

## 5. 압전센서(피에조)를 받았다면

**FSR 과 압전센서는 다른 부품이고, 이 제품에는 FSR 이 맞다.**

| | FSR (힘 감지 저항) | 압전소자 (피에조) |
|---|---|---|
| 생김새 | 얇고 긴 필름, 끝에 동그란 감지부 | 황동색 금속 원판, 가운데 흰 세라믹 |
| 재는 것 | **누르고 있는 힘** (정적) | **힘의 변화·충격** (동적) |
| 가만히 밟고 있으면 | 값이 유지된다 | **값이 0 으로 돌아간다** |
| 배선 | 5V + 10kΩ 분압 | 5V 안 씀. 양단에 1MΩ |

압전소자는 **밟는 순간에만 신호가 나고 유지하면 사라진다.** 이 제품이
알아야 하는 것은 "지금 무게가 어디에 실려 있는가" 이므로 압전소자로는
성립하지 않는다. 충격 감지(발뒤꿈치 착지 시점)에는 쓸 수 있다.

압전소자를 그냥 A0 에 꽂으면 안 된다 — 두드리면 수십 V 가 나오고
음전압도 나와 아두이노 입력이 상할 수 있다. 꼭 시험하려면
**양단에 1MΩ 저항을 병렬로** 달아 전하를 빼 준다.
