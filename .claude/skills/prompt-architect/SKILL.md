# 프롬프트 해체와 재설계

## 이 스킬이 푸는 문제

대부분의 프롬프트 조언은 "역할·과업·맥락·제약·형식"을 채우라고 말한다.
그 다섯은 **요청을 서술**할 뿐 **실행을 서술하지 않는다.**
그래서 그 다섯이 완벽한 프롬프트도 돌리면 실패한다.

실패는 거의 항상 같은 자리에서 난다. 재료가 어디서 오는지 안 적혀 있고,
필요한 도구가 있는지 확인하지 않았고, "좋다"가 숫자로 없고,
완료 판정을 모델이 스스로 타이핑한다.

이 스킬은 프롬프트를 **요청 층 4슬롯 + 실행 층 4슬롯**으로 해체한다.
진단은 단순하다 — 비어 있으면서 결과를 바꾸는 슬롯을 찾는 일이다.

## 8슬롯

### 요청 층 — 없으면 말이 안 되는 프롬프트

| 슬롯 | 묻는 것 | 비면 벌어지는 일 |
|---|---|---|
| **역할** | 어떤 관점에서 판단하는가 | 판단 기준이 없어 무난한 평균값이 나온다 |
| **과업** | 동사 하나로 뭘 하는가 | 여러 일을 조금씩 하다 만다 |
| **맥락** | AI가 모르는 사실은 무엇인가 | 모르는 부분을 그럴듯하게 지어낸다 |
| **산출물** | 무엇을 몇 개, 어떤 형식으로 | 형식이 매번 달라 재사용이 안 된다 |

### 실행 층 — 없으면 돌렸을 때 실패하는 프롬프트

| 슬롯 | 묻는 것 | 비면 벌어지는 일 |
|---|---|---|
| **재료** | 산출물의 원료는 어디서 오는가 | 중간까지 가서 재료가 없다고 멈춘다 |
| **역량** | 필요한 도구·데이터·권한이 실제로 있는가 | 있다고 가정하고 진행하다 뒤늦게 못 한다고 한다 |
| **기준** | 좋고 나쁨의 경계가 숫자로 있는가 / 기준끼리 충돌하면 | 매번 다른 결과가 나오고 근거를 댈 수 없다 |
| **검증** | 완료를 어떻게 판정하는가 | 모델이 스스로 합격을 선언한다 |

**역할 슬롯 주의**: "10년 차 전문가"가 판단 기준을 실제로 바꾸지 않으면 장식이다.
경력 연차보다 *무엇을 우선하는 사람인지*가 훨씬 강하게 작동한다 —
"속도보다 재현성을 택하는 데이터 엔지니어"는 "15년 차 데이터 엔지니어"보다 낫다.

## 세 가지 실패 서명

진단할 때 이 이름들로 부르면 사용자도 같은 것을 보게 된다.

**약속 후 실패** — 역량·재료 슬롯이 비었다.
중간 단계까지 매끄럽게 진행한 뒤 마지막에 "죄송합니다, 이건 만들 수 없습니다"로 끝난다.
가장 나쁜 실패다. 아무것도 못 한 것보다 나쁘다 — 사용자의 시간을 다 쓴 뒤에 실패했기 때문이다.
처방: 약속하기 전에 확인하는 단계를 프롬프트 맨 앞에 둔다.

**조용한 표류** — 기준·재료 슬롯이 비었다.
결과가 나오긴 하는데 매번 다르고, 왜 그렇게 했는지 물으면 근거가 없다.
처방: 임의 판단이 들어가는 자리마다 수치와 우선순위를 박는다.

**셀프 합격** — 검증 슬롯이 선언이다.
`"✓ 완료"`는 모델이 타이핑하면 그만인 문자열이다.
처방: 완료 판정을 측정값으로 바꾼다. 도구가 있는 환경이면 코드가 출력한 숫자, 없으면 사용자가 눈으로 확인할 수 있는 대조 항목.

## 모드 A — 해체 (기존 프롬프트가 있을 때)

사용자가 프롬프트를 붙여넣었거나 파일로 줬을 때.

1. **8슬롯에 배치한다.** 원문의 문장을 슬롯에 나눠 담는다. 어느 슬롯에도 안 들어가는 문장은 따로 표시한다 — 대개 장식이거나 중복이다.
2. **빈 슬롯 중 결과를 바꾸는 것만 고른다.** 비어 있어도 무해한 슬롯이 있다. 짧은 요약 프롬프트에 검증 슬롯이 없는 건 문제가 아니다. *이 과업에서* 그 슬롯이 비면 무슨 일이 벌어지는지 말할 수 없다면 지적하지 마라.
3. **각 지적마다 세 가지를 쓴다**: 무엇이 비었나 / 돌리면 무슨 일이 벌어지나 / 어떻게 채우나. 두 번째가 없으면 잔소리가 된다.
4. **개선판 전문을 낸다.** 발췌나 "이 부분을 이렇게 고치세요"가 아니라, 복사해서 바로 쓸 수 있는 전문.
5. **변경점 표를 붙인다.** 사용자가 무엇을 잃고 무엇을 얻었는지 한눈에 봐야 한다.

원문에 살아 있는 것은 살려라. 좋은 프롬프트를 통째로 다시 쓰면
사용자가 공들여 넣은 도메인 지식이 날아간다. 해체는 재작성이 아니라 보강이다.

## 모드 B — 설계 (목표만 있을 때)

사용자가 "이런 걸 하고 싶은데"라고만 말했을 때.

1. **목표 진술을 8슬롯에 배치한다.** 세 부류로 나뉜다 — 사용자가 말한 것, 목표에서 추론 가능한 것, 정말 알 수 없는 것.

2. **"알 수 없는 것" 중 최대 3개만 묻는다.** 질문을 고르는 기준은 **모르는 것이 아니라 답에 따라 결과물이 달라지는 것**이다.

   합리적 기본값이 있으면 묻지 말고 가정으로 적어라. 사용자는 틀린 가정만 반박하면 된다 — 그게 질문에 답하는 것보다 싸다. 다섯 개를 물어 완벽하게 아는 것보다, 두 개를 묻고 세 개를 가정으로 드러내는 편이 대화 턴도 짧고 사용자가 놓친 선택지도 보인다.

   질문은 한 번에 하나씩. 보기에 ①②③ 번호를 붙이고 마지막 보기는 항상 "④ 추천해 줘". 번호로 답하든 문장으로 답하든 받아라. 보기 밖 답이 오면 되묻지 말고 가장 가까운 보기로 해석한 뒤 한 줄로 확인시킨다.

3. **분석할 수 있는 것을 먼저 분석한다.** 사용자가 파일·코드베이스·문서를 줬다면 질문보다 먼저 읽어라. 읽으면 알 수 있는 것을 묻는 질문은 낭비되는 턴이다.

4. **프로파일을 요약해 확인받는다.** 그다음 프롬프트 전문 + 가정 목록 + 의도적으로 넣지 않은 것.

## 대상 환경에 따라 달라지는 것

목표를 보고 이 프롬프트가 어디서 돌아갈지 판단한 뒤, 해당 항목만 적용한다.

**도구가 있는 환경** (Claude Code, 에이전트, 파일·코드 실행 가능)
- 역량 슬롯이 실제 점검 단계가 된다: 필요한 도구가 있는지 먼저 확인하고, 없으면 축소된 대체 산출물을 제안하고 승인받은 뒤 진행.
- 검증 슬롯이 측정이 된다: 목표값과 실측값을 나란히 놓은 표.
- 단계 사이에 **기계가 읽는 인계 형식**을 둔다. 사람이 읽는 표만 있으면 다음 단계에서 모델이 표를 다시 읽어 옮기고, 그 전사 구간에서 값이 조용히 어긋난다. 표(승인용)와 JSON(실행용)을 함께 내게 하고 이후 단계는 JSON만 참조하게 한다.
- 재현 수단을 산출물에 넣는다: 사용자가 직접 다시 돌릴 수 있는 스크립트나 설정.

**채팅만 있는 환경** (웹 UI, 텍스트만)
- 역량 슬롯은 "무엇을 못 하는지 먼저 밝히기"로 축소된다.
- 검증은 사용자가 눈으로 대조할 수 있는 체크 항목이어야 한다.
- 길이와 형식 통제가 훨씬 중요해진다. 원하는 출력의 짧은 예시 하나가 형식 지시 열 줄보다 강하다.

## 흔한 함정

**존재하지 않는 능력 지정.** 도구 이름을 넣을 때 그 도구가 그 일을 하는지 확인하라.
(오디오 *처리* 라이브러리에게 소리를 *합성*하라고 시키는 식의 실수가 흔하다.)
확신이 없으면 도구를 지목하는 대신 "필요한 도구가 있는지 먼저 확인하라"로 쓴다.

**측정할 수 없는 지표를 정식 명칭으로 부르기.** 근사치를 정식 이름으로 부르면
모델은 근사치를 계산해 놓고 정식 명칭으로 보고한다. 사용자는 틀린 숫자를 믿게 된다.
프롬프트에 이렇게 쓴다: "그 지표를 측정할 수 없으면 그 단어를 쓰지 말고 실제 측정한 것의 이름으로 보고하라."

**강한 어휘 남발.** "절대", "반드시", "무조건"이 스무 번 나오면 스무 개 다 약해진다.
정말 지켜야 할 두세 개에만 쓰고, 나머지는 *왜* 그래야 하는지 한 줄로 설명하라.
이유를 이해한 모델은 예상 못 한 상황에서도 의도대로 판단한다.

**질문을 분석보다 앞에 두기.** 자료를 받기 전에 자료에 관해 묻는 구조는 낭비되는 턴이다.

**스킵 규칙 없는 순서 강제.** "순서 엄수"라고만 쓰면 사용자가 이미 답한 것도 다시 묻는다.
"이미 밝힌 항목은 건너뛰고 '○○로 이해했습니다' 한 줄로 대체한다"를 함께 넣어라.

## 출력 형식

### 모드 A (해체)

```
## 슬롯 분해
| 슬롯 | 현재 내용 | 상태 |
(상태: 채워짐 / 약함 / 비어 있음)

## 진단
비어 있으면서 결과를 바꾸는 슬롯만, 중요도 순.
각 항목: 무엇이 비었나 → 돌리면 무슨 일이 벌어지나 → 어떻게 채우나

## 개선판
(복사해서 바로 쓸 수 있는 전문)

## 변경점
| 영역 | 이전 | 이후 |

## 남은 한계
개선판으로도 해결되지 않는 것. 없으면 이 절을 생략한다.
```

### 모드 B (설계)

```
(질문 최대 3개, 한 번에 하나씩)

## 이렇게 이해했습니다
목표 / 산출물 / 대상 환경 요약 — 틀린 곳을 짚어 달라고 요청

## 프롬프트
(전문)

## 가정
묻지 않고 채운 것. 사용자가 반박할 수 있게 각각 한 줄로.

## 의도적으로 넣지 않은 것
과잉 설계를 피하려고 뺀 것. 필요하면 추가하겠다고 알린다.
```

## 자기 점검

프롬프트를 내놓기 전에 스스로 물어라 — 이 프롬프트를 처음 보는 모델이
**이 일을 할 도구가 있는지 알 수 있는가, 재료를 어디서 구할지 알 수 있는가,
다 됐다는 걸 어떻게 아는가.** 셋 중 하나라도 답이 "모른다"면 아직 덜 됐다.
