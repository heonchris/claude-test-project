# 데이터 규격 (센서 ↔ 앱)

이 문서가 인수인계의 핵심입니다. **앱 코드는 참고용이고, 이 규격이 실제 계약 지점입니다.**
앱을 Flutter·React Native 등 다른 것으로 다시 만들더라도 이 규격은 그대로 씁니다.

---

## 1. 채널 구성

발당 8채널, 양발 16채널.

| ch | 발 | 위치 | ch | 발 | 위치 |
|---|---|---|---|---|---|
| 1 | 왼 | 엄지 | 9  | 오른 | 엄지 |
| 2 | 왼 | 2–3지 | 10 | 오른 | 2–3지 |
| 3 | 왼 | 제1중족골두 | 11 | 오른 | 제1중족골두 |
| 4 | 왼 | 제2–3중족골두 | 12 | 오른 | 제2–3중족골두 |
| 5 | 왼 | 제5중족골두 | 13 | 오른 | 제5중족골두 |
| 6 | 왼 | 중족부 외측 | 14 | 오른 | 중족부 외측 |
| 7 | 왼 | 뒤꿈치 내측 | 15 | 오른 | 뒤꿈치 내측 |
| 8 | 왼 | 뒤꿈치 외측 | 16 | 오른 | 뒤꿈치 외측 |

**채널 번호가 곧 배열 순서입니다.** 위 표는 **최종 인솔 기준의 약속**입니다.

다만 브링업 중에는 배선 순서가 표와 다를 수밖에 없으므로, 앱에서
**[설정] → [센서 위치 설정]** 으로 채널↔자리를 바꿀 수 있습니다
(`js/12-mapping.js`, localStorage 에 저장). 펌웨어를 고치거나 선을
다시 뽑을 필요가 없습니다. 이 매핑은 **화면 표시에만** 적용되며
패킷 규격 자체는 위 표 그대로입니다.

센서의 물리적 좌표는 `js/01-config.js` 의 `SENSORS` 배열에 있습니다.
실제 인솔 설계가 확정되면 그 좌표만 고치면 됩니다.

## 2. BLE 패킷

### 서비스 / 특성

**모듈마다 UUID 가 다릅니다.** 앱은 아래를 위에서부터 시도해 먼저 잡히는 것을 씁니다.

| 쓰는 경우 | Service | Notify | 비고 |
|---|---|---|---|
| **시중 모듈** (HM-10·AT-09·BT05) | `0000FFE0-…` | `0000FFE1-…` | CC2541 공장 기본값. **현재 실기기 테스트는 이쪽** |
| 자체 펌웨어 | `0000FFF0-…` | `0000FFF1-…` | 임시값. 펌웨어 확정 시 교체 |

자체 펌웨어용 Write 특성(명령: 영점·샘플링 변경)은 `0000FFF2-…` 로 둔다. 미구현.

> 처음 이 문서는 FFF0/FFF1 만 적어 두었는데, 시중 모듈을 그냥 꽂으면
> **FFE0 이라 앱이 기기를 찾지도 못한다.** 2025-10 에 `js/11-ble.js` 가
> 두 가지를 모두 시도하도록 고쳤다.

### 패킷 구조 — 34바이트 고정

```
오프셋  크기  내용
  0      1   헤더 0xA5 (패킷 시작 식별)
  1      1   시퀀스 번호 0~255 순환 (유실 감지용)
  2      2   ch1  uint16 little-endian
  4      2   ch2
  ...
 32      2   ch16
```

- **바이트 순서: little-endian**
- **값 범위: 0 ~ 1023** (아두이노 10bit ADC 기준)
  - ESP32(12bit)로 바꾸면 0~4095. 이 경우 `01-config.js` 의 `MAX_RAW` 만 고치면
    앱 전체가 따라갑니다.
- **0xFFFF** 는 해당 채널 미연결/오류를 뜻합니다. 앱은 이 값을 0 으로 취급하지 말고
  별도 표시해야 합니다. (`js/08-health.js` 의 `sanitize()` 에 구현되어 있습니다)

### ⚠ 전송 단위 — 미해결

**34바이트는 BLE 한 번에 보낼 수 있는 기본 크기(20바이트)를 넘습니다.**

HM-10·AT-09·BT05 처럼 흔히 쓰는 모듈은 투명 전송 모드에서 한 번에
20바이트까지만 보냅니다. 34바이트를 쓰면 **20 + 14 로 쪼개져** 도착합니다.
그런데 `js/11-ble.js` 의 `handlePacket()` 은 길이가 정확히 34가 아니면
버리므로, 이대로 연결하면 **모든 패킷이 버려집니다.**

8채널 연동 전에 셋 중 하나를 정해야 합니다.

**→ A(재조립)로 해결했습니다.** `js/11-ble.js` 가 받은 조각을 이어 붙였다가
헤더 `0xA5` 를 찾아 34바이트가 모이면 한 패킷으로 넘깁니다. 규격은 그대로 두고
앱만 고쳤으므로 펌웨어 쪽 제약이 없습니다.

검증한 것 (2025-10, 모의 스트림)

| 경우 | 결과 |
|---|---|
| 20바이트씩 분할 수신 | 3/3 패킷 복원 |
| 1바이트씩 분할 수신 | 복원됨 |
| 앞에 쓰레기 바이트가 섞임 | 재동기화 후 복원 |
| 데이터 안에 `0xA5` 가 들어 있음 | 복원됨 |
| 0·1·255·256·1023 값 왕복 | 전부 일치 |

남은 한계: 데이터 안의 `0xA5` 가 패킷 경계와 우연히 겹치면 한 번 어긋날 수
있습니다. 다음 패킷에서 순번이 튀므로 스스로 다시 맞지만, 완전히 막으려면
나중에 **체크섬**을 패킷 끝에 추가하는 것이 좋습니다.

### 전송 주기

30 Hz (33ms 간격) — **단, UART 속도가 받쳐 줄 때만.**

```
34 바이트 × 30 Hz = 1,020 B/s
9600 baud 의 실제 한도 ≈ 960 B/s      → 들어가지 않는다
```

블루투스 모듈의 기본 UART 속도는 9600 이다. 그대로 두면 30Hz 가 안 나온다.

| 선택 | 방법 |
|---|---|
| 속도를 올린다 | 모듈에 `AT+BAUD4`(38400) 등을 보내고, 스케치의 `bt.begin()` 도 같이 바꾼다 |
| 주기를 낮춘다 | 브링업 단계에서는 10Hz(340 B/s)로 충분하다. `hardware/step3_packet_stream` 이 이 방식 |

AT 명령 번호는 모델마다 다르므로 `AT+HELP` 또는 모듈 문서를 확인한다.

### 대역폭 검증

```
34 바이트 × 30 Hz = 1,020 B/s ≈ 8.2 kbps
```

BLE 4.0 의 실효 처리량이 대략 5~10 kB/s 이므로 **여유가 충분합니다.**
채널을 32개로 늘려도(66바이트 × 30Hz ≈ 16 kbps) 문제없습니다.

## 2-1. 플랫폼별 연결 방식 ★

**같은 규격이지만 연결하는 주체가 다릅니다.**

| 플랫폼 | 연결 주체 | 필요한 것 |
|---|---|---|
| **안드로이드** | 웹 앱이 직접 (`navigator.bluetooth`) | 크롬·엣지·삼성인터넷. **앱 설치 불필요** |
| **아이폰** | 네이티브 앱의 Swift(CoreBluetooth) | 맥북 + Xcode. 웹에서는 불가능 |

아이폰은 사파리를 포함한 **모든 브라우저**가 웹 블루투스를 지원하지 않습니다.
아이폰의 모든 브라우저가 같은 엔진(WebKit)을 쓰기 때문에 크롬을 깔아도
동일합니다.

안드로이드 구현은 `js/11-ble.js` 에 완성되어 있습니다.
아이폰은 Swift 에서 받은 값을 `evaluateJavaScript` 로
`INSOLE.sensor.values` 에 넣어 주고 `INSOLE.health.markFrame()` 을
호출하면 나머지가 동일하게 동작합니다.

## 3. 앱이 기대하는 형태

BLE 패킷을 풀어서 아래 형태로 만들면 앱의 나머지가 전부 동작합니다.

```js
{
  L: [ch1, ch2, ch3, ch4, ch5, ch6, ch7, ch8],      // 각 0 ~ 1023
  R: [ch9, ch10, ch11, ch12, ch13, ch14, ch15, ch16]
}
```

구현 위치: **`js/11-ble.js`**. (`02-sensor.js` 의 `connectBLE()` 주석은
구현 전에 남긴 안내로, 실제 코드는 `11-ble.js` 에 있습니다.)
`11-ble.js` 가 값을 채운 뒤 `INSOLE.health.markFrame()` 을 호출하면
나머지 화면이 전부 따라 움직입니다.

## 4. 아직 정해지지 않은 것

인수인계 시점에 **미확정**인 항목입니다. 킥오프에서 정해야 합니다.

| 항목 | 왜 필요한가 |
|---|---|
| 실제 서비스/특성 UUID | 위 표는 임시값 |
| 영점(zero) 보정 절차 | FSR 은 개체차가 커서 착용 시 기준값을 잡아야 함 |
| 센서 물리 좌표 확정 | 히트맵 정확도가 여기 달려 있음 |
| 배터리·연결상태 알림 규격 | 현재 UI 는 하드코딩된 82% 표시 |
| 채널 오류 시 UI 처리 | 0xFFFF 를 어떻게 보여줄 것인가 |
| 저장 스키마 | 세션/프레임/사용자/리포트 테이블 (사업 정의서 6단계) |

## 5. 저장 스키마 초안 (참고)

사업 정의서 6단계에서 확정할 내용이지만, 프로토타입이 다루는 데이터 기준으로는
아래 정도면 충분합니다.

```
session
  id, user_id, started_at, ended_at, duration_sec, reps,
  avg_lr_ratio, avg_ap_ratio, max_lr_dev, cop_range_mm, verdict

frame                       -- 원본 스트림. 용량이 크므로 보관 정책 필요
  session_id, t_ms, ch1 … ch16

report
  session_id, title, message, severity, created_at
```

30Hz × 16채널 × 60초 = 28,800 값/분입니다. **원본 프레임을 전부 서버에 올릴지,
요약만 올릴지는 초기에 정해야 합니다.** 나중에 바꾸면 앱과 서버를 모두 고쳐야 합니다.
