# 데이터 규격 (센서 ↔ 앱)

이 문서가 인수인계의 핵심입니다. **앱 코드는 참고용이고, 이 규격이 실제 계약 지점입니다.**
앱을 Flutter·React Native 등 다른 것으로 다시 만들더라도 이 규격은 그대로 씁니다.

---

## 1. 채널 구성

발당 8채널, 양발 16채널.

| ch | 발 | 위치 | ch | 발 | 위치 |
|---|---|---|---|---|---|
| 1 | 왼 | 엄지 | 9  | 오른 | 엄지 |
| 2 | 왼 | 2–3지 | 10 | 오른 | 2–3지 |
| 3 | 왼 | 제1중족골두 | 11 | 오른 | 제1중족골두 |
| 4 | 왼 | 제2–3중족골두 | 12 | 오른 | 제2–3중족골두 |
| 5 | 왼 | 제5중족골두 | 13 | 오른 | 제5중족골두 |
| 6 | 왼 | 중족부 외측 | 14 | 오른 | 중족부 외측 |
| 7 | 왼 | 뒤꿈치 내측 | 15 | 오른 | 뒤꿈치 내측 |
| 8 | 왼 | 뒤꿈치 외측 | 16 | 오른 | 뒤꿈치 외측 |

**채널 번호가 곧 배열 순서입니다.** 순서가 바뀌면 히트맵의 위치가 전부 어긋납니다.

센서의 물리적 좌표는 `js/01-config.js` 의 `SENSORS` 배열에 있습니다.
실제 인솔 설계가 확정되면 그 좌표만 고치면 됩니다.

## 2. BLE 패킷

### 서비스 / 특성

| 항목 | UUID | 비고 |
|---|---|---|
| Service | `0000FFF0-0000-1000-8000-00805F9B34FB` | **임시값 — 펌웨어 확정 시 교체** |
| Characteristic (Notify) | `0000FFF1-0000-1000-8000-00805F9B34FB` | 측정값 스트리밍 |
| Characteristic (Write) | `0000FFF2-0000-1000-8000-00805F9B34FB` | 명령 (영점, 샘플링 변경) |

### 패킷 구조 — 34바이트 고정

```
오프셋  크기  내용
  0      1   헤더 0xA5 (패킷 시작 식별)
  1      1   시퀀스 번호 0~255 순환 (유실 감지용)
  2      2   ch1  uint16 little-endian
  4      2   ch2
  ...
 32      2   ch16
```

- **바이트 순서: little-endian**
- **값 범위: 0 ~ 1023** (아두이노 10bit ADC 기준)
  - ESP32(12bit)로 바꾸면 0~4095. 이 경우 `01-config.js` 의 `MAX_RAW` 만 고치면
    앱 전체가 따라갑니다.
- **0xFFFF** 는 해당 채널 미연결/오류를 뜻합니다. 앱은 이 값을 0 으로 취급하지 말고
  별도 표시해야 합니다. (현재 프로토타입은 미구현)

### 전송 주기

30 Hz (33ms 간격)

### 대역폭 검증

```
34 바이트 × 30 Hz = 1,020 B/s ≈ 8.2 kbps
```

BLE 4.0 의 실효 처리량이 대략 5~10 kB/s 이므로 **여유가 충분합니다.**
채널을 32개로 늘려도(66바이트 × 30Hz ≈ 16 kbps) 문제없습니다.

## 3. 앱이 기대하는 형태

BLE 패킷을 풀어서 아래 형태로 만들면 앱의 나머지가 전부 동작합니다.

```js
{
  L: [ch1, ch2, ch3, ch4, ch5, ch6, ch7, ch8],      // 각 0 ~ 1023
  R: [ch9, ch10, ch11, ch12, ch13, ch14, ch15, ch16]
}
```

구현 위치: `js/02-sensor.js` 의 `connectBLE()`. 그 파일 하나만 고치면 됩니다.

## 4. 아직 정해지지 않은 것

인수인계 시점에 **미확정**인 항목입니다. 킥오프에서 정해야 합니다.

| 항목 | 왜 필요한가 |
|---|---|
| 실제 서비스/특성 UUID | 위 표는 임시값 |
| 영점(zero) 보정 절차 | FSR 은 개체차가 커서 착용 시 기준값을 잡아야 함 |
| 센서 물리 좌표 확정 | 히트맵 정확도가 여기 달려 있음 |
| 배터리·연결상태 알림 규격 | 현재 UI 는 하드코딩된 82% 표시 |
| 채널 오류 시 UI 처리 | 0xFFFF 를 어떻게 보여줄 것인가 |
| 저장 스키마 | 세션/프레임/사용자/리포트 테이블 (사업 정의서 6단계) |

## 5. 저장 스키마 초안 (참고)

사업 정의서 6단계에서 확정할 내용이지만, 프로토타입이 다루는 데이터 기준으로는
아래 정도면 충분합니다.

```
session
  id, user_id, started_at, ended_at, duration_sec, reps,
  avg_lr_ratio, avg_ap_ratio, max_lr_dev, cop_range_mm, verdict

frame                       -- 원본 스트림. 용량이 크므로 보관 정책 필요
  session_id, t_ms, ch1 … ch16

report
  session_id, title, message, severity, created_at
```

30Hz × 16채널 × 60초 = 28,800 값/분입니다. **원본 프레임을 전부 서버에 올릴지,
요약만 올릴지는 초기에 정해야 합니다.** 나중에 바꾸면 앱과 서버를 모두 고쳐야 합니다.
